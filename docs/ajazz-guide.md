# Ajazz AK820 Pro: руководство по поддержке + read-only диагностика

> **Кому:** владельцу **Ajazz AK820 Pro** (ревизии USB `0C45:8009` / `0C45:800A` / `0C45:8099`), у которого есть реальное железо.
>
> **Зачем:** драйвер `src/devices/ajazz_ak820.rs` написан по открытому ресёрчу (wsclx / ak820pro-modder, протокол fw 1.07); **часть выводов с 2026-11-11 проверена на живом железе** ревизии `0C45:8009` (журнал 10.53/10.54/10.60/10.63/10.106/10.114/10.115): control-канал `0xFF13` (подсветка/время/сон/заряд/per-key) работает, wsclx `0xFF68` (TFT и часть команд) — нет. При этом **keymap и макросы, по реверсу официального ПО, живут на том же `0xFF13`** (`0x11`/`0x27` и `0x19`/`0x15`) — команды известны, код просто ещё не переведён туда. Сводный статус — в разделе A. Ваши read-only снимки помогут продвинуть остальное.
>
> **ВАЖНО:** этот документ и скрипт — **ТОЛЬКО ЧТЕНИЕ**. Ни одной write-команды в клавиатуру не отправляется: сбор делает лишь GET-запросы и системные команды (`lsusb`). Запись (TFT-картинки, макросы, keymap, sleep, синк времени) в этом гайде не запускается.

## A. Статус поддержки (ревизия `0C45:8009`, по состоянию на 2026-11-14)

Ajazz AK820 Pro — Sonix SN32F299. **Рабочий канал один — control `0xFF13`** (feature-репорты, на провод уходит 65 байт = `0x00` + 64). Всё, что было написано по ресёрчу wsclx под `0xFF68` (транспорт `0xAA`/`0x55`, keymap, макросы, TFT), на этой ревизии не отвечает. **Важно:** реверс официального ПО (`Twyx22/ak820-center`, `PROTOCOL.md`, сверен с `deddroid/ak820-rs`) показывает, что **keymap и макросы живут на том же рабочем `0xFF13`** (`0x11`/`0x27` — слои keymap, `0x19`+`0x15` — макросы); код драйвера просто пока ходит в мёртвый `0xFF68`.

Легенда: ✅ проверено на живом железе · 🟡 реализовано, ждёт живой проверки · ⛔ не работает на ревизии 8009 · 🚫 невозможно/закрыто.

| Функция | Канал / команда | Статус | Комментарий |

| Синхронизация времени | `0xFF13`: `0x28` | ✅ | десятичный формат (не BCD) |

| Per-key: сохранённая таблица | `0xFF13`: `0x23` (запись), `0xF5` (чтение) | 🟡 | 576 Б = 144 слота × `[index,R,G,B]` + `AA 55`; read-modify-write |
| Per-key: живые кадры | `0xFF13`: `0x20` | 🟡 | 512 Б, без `FINISH`; так работает `render_frame` |

| Яркость TFT | `0xFF67` | ⛔ | команда не декодирована (этап 5) |
| Polling rate / debounce | `0xFF68` | ⛔ | не декодировано (этап 7) |
| Энкодер | — | 🚫 | firmware-fixed (Volume/Mute) |

| 2.4G-донгл `0C45:FDFD` | `0xFF60` (MI_03, 32 Б) | 🟡 | транспорт и эхо-ответы живы, запись `SET_LED_EFFECT` не дожата (этап 6) |

### A2. Как выглядит железо (проверено 2026-11-11)

Три HID-интерфейса (usage pages) по ресёрчу: **control `0xFF13`**, **data/командный `0xFF68`**, **TFT `0xFF67`**. Драйвер сам выбирает нужный интерфейс по usage page.

> **Проверено на живом железе (2026-11-11, ревизия `0C45:8009`) — картина другая:**
> интерфейсов **четыре** — boot-клавиатура (usage `0x01/0x06`), consumer/system, **`0xFF68`** и **`0xFF13`**; **`0xFF67` (TFT) отсутствует**.
> Работает **только `0xFF13`** (подсветка 20 режимов, синк времени, сон, заряд АКБ, per-key таблица `0x23` и live-кадры `0x20`; **сюда же по реверсу относятся keymap `0x11`/`0x27` и макросы `0x19`/`0x15`**). **`0xFF68` мёртв** — принимает запись любого размера, но не отвечает ни на одну GET-команду; TFT-интерфейс `0xFF67` на 8009 **отсутствует**. Поэтому в текущей версии драйвера keymap/макросы/TFT честно отдают `Unsupported`, хотя команды keymap и макросов уже известны и ждут переноса на `0xFF13` (этапы 3–4).
> 2.4 GHz донгл — отдельное устройство `0C45:FDFD` (интерфейс `MI_03`, usage page `0xFF60`, кадры 32 Б wsclx + checksum); GET-команды эхо-отвечают, но `SET_LED_EFFECT` визуально не применяется — формат/commit не выяснен.

### A3. Открытые вопросы (что нужно подтвердить)

1. ~~Совпадают ли **usage pages** и число интерфейсов с ожидаемыми?~~ — **ПРОВЕРЕНО 2026-11-11:** интерфейсов 4 (boot kbd, consumer, `0xFF68`, `0xFF13`), `0xFF67` (TFT) нет.
2. ~~Отвечает ли транспорт `0xAA`/`0x55` на GET-команды?~~ — **ПРОВЕРЕНО:** `0xFF68` не отвечает ни на одну (keymap/макросы/матрицы недоступны); на донгле `0xFF60` GET-команды только эхо-отвечают без данных. Per-key и батарея оказались **не** в `0xFF68`, а в `0xFF13` (см. A4).
3. ~~Где именно лежит **батарея**?~~ — **ПРОВЕРЕНО по реверсу, живой тест ждёт:** запрос `0x20 0x01` на `0xFF13`, уровень в 4-м байте ответа.
4. ~~Читаются ли **keymap Default/FN1** и заводские матрицы?~~ — **чтения нет.** На рабочем `0xFF13` есть только **запись** слоёв (`0x11` base, `0x27` Fn, 576 Б на слой); команд чтения keymap/заводских матриц не существует — официальное ПО держит состояние на стороне ПК (`config.xml`). Заводская base-раскладка теперь берётся из ассета установщика (`data/ajazz/rgb-keyboard.xml` → `factory_keymap_ak820()`), Fn-слой в установщике отсутствует. Перед первым remap всё равно нужен авто-бэкап (см. A1, этап 3).
5. Формат **LED-эффекта** (16-байтный payload) — не читается; подсветка управляется через `0xFF13` (эффекты `0x00..0x13`, яркость/скорость 0..5).
6. Макросы: **формат записи найден в реверсе** — `0x19` (открыть сессию) → `0x15` (value = число блоков + 1) → 400 Б index (100 слотов × u16 LE) + блоки данных + трейлер `AA 55` → `COMMIT`. **Чтения макросов нет** (см. A1, этап 4).
7. **Главный блокер:** нужен usbmon-захват трафика официального Windows-ПО, чтобы оживить `0xFF68`/TFT и 2.4G-запись — без него не гадаем (политика «НЕ ГАДАТЬ»). Для keymap/макросов он **не нужен** — команды уже известны из реверса (`0xFF13`), но проверять их на живом железе всё равно придётся с авто-бэкапом.

### A4. Транспорт `0xFF13` в драйвере (этапы 0–2, реверс официального ПО)

Основа — разбор официального ПО: `Twyx22/ak820-center` (`app/src/device.cpp`) и `deddroid/ak820-rs` (`src/device.rs`, `src/protocol.rs`), сверено с `gohv/EPOMAKER-Ajazz-AK820-Pro`.

- **Кадр:** 64 логических байта; на провод уходит 65 (ведущий report id `0x00` + 64). Командный пакет: `[0]=0x04`, `[1]=команда`, `[2]=аргумент`, `[8..10]=count` (LE) — число следующих data-пакетов/блоков.
- **Команды:** `0x18` START, `0x13` MODE (подсветка), `0x28` TIME, `0x17` SLEEP, `0x02` COMMIT, `0x23` KEY_COLORS (сохранённая таблица per-key), `0x20` LIVE_COLORS (живой кадр), `0xF5` чтение таблицы цветов, `0xF0` FINISH, `0x20 0x01` — запрос заряда.
- **Keymap / макросы (по реверсу, код ещё не переведён сюда):** `0x11` — base-слой keymap, `0x27` — Fn-слой (по 576 Б: 144 слота × 4 Б + `AA 55`), `0x19` — открыть сессию макросов, `0x15` — данные макросов (400 Б index + блоки + `AA 55`). Записываются тем же приёмом `START → <команда> с count → блоки → COMMIT → FINISH`. Команд **чтения** keymap/макросов нет.
- **Запись таблицы:** `START` → `<команда>` с count = число блоков → данные по 64 Б → `COMMIT` → `FINISH`. Если `COMMIT` вернул 16-битную сумму, драйвер сверяет её с посчитанной по отправленным данным и при несовпадении повторяет (до 3 попыток). Отсутствие ответа (`Broken pipe` на GET_REPORT) провалом НЕ считается — запись уже ушла.
- **Per-key сохранённая таблица (`0x23`):** 576 Б = 144 слота × `[index, R, G, B]` + трейлер `AA 55` в двух последних байтах. Чтение (`0xF5`, count=9) отдаёт упакованный RGB (432 Б = 144×3), после чего драйвер делает read-modify-write одной клавиши.
- **Per-key живой кадр (`0x20`):** 512 Б = 128 групп `[index, R, G, B]`, нулевое дополнение; без `FINISH` — прошивка сама возвращается к сохранённому эффекту, когда кадры перестают приходить. Так работает `render_frame` для разноцветных кадров.
- **`kbc rgb 0C45:8009 --mode custom --color RRGGBB`** заливает все 144 слота одним цветом и включает режим Custom (то же делает GUI-студия).
- **Батарея:** пакет `0x20 0x01`; ответ проверяется по первым двум байтам, уровень — 4-й байт; `0xFF` трактуется как «на проводе» → 100 %.
- **НЕ проверено на живом железе:** запись/чтение таблицы `0x23`, живые кадры `0x20`, заряд АКБ. Проверены только подсветка, время и сон (журнал 10.112). При странностях первым делом смотреть `kbc rgb ... --mode static` — этот путь подтверждён.

## C. Команда `kbc ajazz-diag` и формат дампа

`kbc ajazz-diag <VID:PID>` открывает командный интерфейс (`0xFF68`) и последовательно выполняет read-only GET-команды. Формат вывода — по строке на секцию, `ключ=hex`; если команда не ответила — `ключ_error=…`, дамп продолжается.

> **На ревизии `0C45:8009` (живое железо, 2026-11-11) `0xFF68` не отвечает**, поэтому весь дамп придёт как `*_error=Protocol` — это ожидаемый и полезный результат (ревизия/прошивка отличается от ресёрча wsclx), а не сбой скрипта.

| Ключ | Команда | Размер | Смысл |
|---|---|---|---|
| `device_info` | `GET_DEVICE_INFO` (16) | 48 Б | info-структура; `battery=` — байт `[17]` |
| `led_effect` | `GET_LED_EFFECT` (19) | 16 Б | текущий глобальный эффект; `led_effect_mode=` — байт `[0]` |
| `game_mode` | `GET_GAME_MODE` (17) | 56 Б | game-mode-блок (задел) |
| `custom_led` | `GET_CUSTOM_LED_DATA` (20) | 512 Б | per-key буфер 128 × RGBA |
| `keymap_base` | `GET_KEY` (18) | 512 Б | текущий базовый слой |
| `keymap_fn` | `GET_FN_KEY` (22) | 512 Б | текущий Fn-слой |
| `keymap_default_base` | `GET_DEFAULT_KEY_MATRIX` (31) | 512 Б | заводской базовый слой |
| `keymap_default_fn` | `GET_DEFAULT_FN_KEY_MATRIX` (28) | 512 Б | заводской Fn-слой |
| `macros_index` | `GET_MACRO` (21) | 400 Б | index макросов (100 слотов × 4 Б LE) |
| `macros_count`, `macro_<id>` | `GET_MACRO` (21) | — | число и декодированные события макросов |

Декодирование, которое делает команда (только достоверное):
- `battery=` — `device_info[17]` (0..100);
- `led_effect_mode=0xNN` — первый байт LED-эффекта (`0x00..0x13` аппаратные, `0x80` Custom);
- `macro_<id>=delay:keycode:family:press,…` — события макроса.

> Все команды — **GET**. Команды `SET_*` (34/35/36/37/38), `SET_FACTORY_RESET` (15), TFT (80/81) и control-канал `0xFF13` этой командой **не используются**.

### Ручной запуск отдельных шагов (если нужно точечно)

```bash
KBC=target/release/kbc

$KBC list
$KBC info 0C45:8009
$KBC probe 0C45:8009          # фактически на 8009: boot-kbd, consumer, data 0xFF68, control 0xFF13 (TFT 0xFF67 нет)

```

## D. Протокол (для тех, кто хочет проверить вручную)

### D1. Транспорт

> На ревизии 8009 этот транспорт не отвечает (см. раздел A); раздел актуален для других ревизий и как справка по wsclx.

64-байтные **output-репорты**, `REPORT_ID = 0`. Кадр запроса:

```
[0] = 0xAA        (MAGIC_OUTGOING)
[1] = cmd         (команда)
[2] = len         (длина полезной нагрузки)
[3] = addr_lo     (адрес, младший байт)
[4] = addr_hi     (адрес, старший байт)
[5] = 0
[6] = last        (1 — последний чанк)
[7] = 0
[8..64) = payload (до 56 байт)
```

Ответ приходит как input-репорт, начинается с `0x55` (`MAGIC_INCOMING`), команда — в байте `[1]`, данные — с байта `[8]`.

### D2. Команды (GET — read-only; SET — сюда НЕ входят)

| Код | Имя | Код | Имя |
|---|---|---|---|
| `16` (0x10) | GET_DEVICE_INFO | `34` (0x22) | SET_KEY |
| `17` (0x11) | GET_GAME_MODE | `35` (0x23) | SET_LED_EFFECT |
| `18` (0x12) | GET_KEY | `36` (0x24) | SET_CUSTOM_LED_DATA |
| `19` (0x13) | GET_LED_EFFECT | `37` (0x25) | SET_MACRO |
| `20` (0x14) | GET_CUSTOM_LED_DATA | `38` (0x26) | SET_FN_KEY |
| `21` (0x15) | GET_MACRO | `15` (0x0F) | SET_FACTORY_RESET |
| `22` (0x16) | GET_FN_KEY | `80` (0x50) | SET_TFT_USER_ANIMATION |
| `28` (0x1C) | GET_DEFAULT_FN_KEY_MATRIX | `81` (0x51) | SET_TFT_BUILT_IN_INDEX |
| `31` (0x1F) | GET_DEFAULT_KEY_MATRIX | | |

### D3. Многочанковые блоки (512 Б keymap, 512 Б custom-LED, макросы)

Большие блоки читаются пачками по **56 байт**: для каждого чанка отправляется кадр с `addr = база + i*56`, `len = размер чанка`, `last = 1` только на последнем. Драйвер ждёт ответ с той же командой и склеивает payload’ы (`get_many`/`get_many_at`).

### D4. Keymap-слот (4 байта)

| Байт 0 (page) | Смысл | Декодирование |
|---|---|---|
| `0` | Default/пусто | `None` |
| `2` | клавиша | `Press(bytes[2])` |
| `3` | media/consumer | `Media(bytes[1] | bytes[2]<<8)` |
| `6` | макрос | `Macro(bytes[1])` |
| `10` | Fn-слой | `FnLayer(bytes[1])` |

Модификатор кодируется как page `2` + `0xE0+m` (поэтому декодируется обратно как `Press(0xE1…)`, а не `Modifier` — особенность формата wsclx).

## E. Что искать в присланном дампе

> Для ревизии `0C45:8009` это уже пройдено (см. раздел A и журнал 10.106/10.114/10.115). Инструкция ниже — для **других ревизий** (`0x800A`, `0x8099`) и новых прошивок.

- **`03-probe.txt`**: есть ли интерфейсы с usage pages `0xFF13`, `0xFF68`, `0xFF67`. Расхождение — важный сигнал о другой ревизии/прошивке.
- **`05-ajazz-diag.txt`**:
  - `battery=` — правдоподобные 0..100?
  - `device_info=…` — первые байты (прошивка/версия, если видно);
  - `led_effect_mode=0xNN` — совпадает с текущим визуальным эффектом?
  - `keymap_base` / `keymap_fn` — не нули ли (нули = канал не читается);
  - `macros_count` и `macro_*`;
  - строки `*_error=Protocol` — какая именно команда не ответила.
- **`06-keymap-list.txt`**: ненулевые назначения слотов (или «все Default»).
- **`08-uevent.txt`**: соответствие hidraw ↔ usage page.

Если какая-то команда вернула `Protocol error` — **это тоже результат** (канал отличается от ожидаемого). Приложите вывод как есть, не «чистите».
