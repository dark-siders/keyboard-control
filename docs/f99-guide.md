# AULA F99: руководство по полной поддержке + формат подсветки

> **Кому:** владельцу **AULA F99** (уже присылавшему живую диагностику — журнал 10.70/10.78) и тем, кто хочет довести поддержку F99 в Keyboard-Center до полной.
>
> **Что здесь:** (A) что уже поддерживается; (B) пошагово, что снять с железа, чтобы закрыть оставшиеся пробелы (ремап, debounce/sleep); (C) полная информация о формате передачи цветов (для тех, кто хочет писать свой интерпретатор GIF в подсветку); (D) ответ на вопрос «как принять участие/оформить md». Отдельно — подтверждённая живой диагностикой карта слотов F99 (см. A2).

## A. Что уже поддерживается у F99 (проверено)

Реальный USB PID F99 — `258A:010C` (общий с F75; модель различается по PSD, `0xA4` — журнал 10.70). Сканер и `kbc` понимают это. Уже работают:

- **Host-подсветка** — direct-канал, 113 LED (`render_frame`), keepalive-поток (10.10/10.55);
- **Host-эффекты** — Static/Дыхание/Волна/Спектр/Риппл/Дождь/Реактивная через общий движок `host_frame_with` (10.55);
- **Конфиг-регион** — чтение/запись (`06 84`/`06 04`, 520 байт), слоты эффектов **34 пары `[58..125]`** (10.78);
- **Сохранение в память** — эффект `data[10]`, свет вкл/выкл (все слоты `a=09/00`), `save_effect_with_style` (10.78);
- **Чтение keymap** Default+FN1 (`06 83`, read-only) — работает (10.75);
- **2.4G-ресивер** — батарея (0x05→0x0A), эффекты/яркость/скорость в слоты, селектор `led[10]` (10.43–10.50);
- **Цветовая таблица** `06 8A` читается (512 Б, модель `A4` в трейлере — 10.70).

## B. Что ещё нужно с железа для полной поддержки

Ниже — команды и сценарии, закрывающие открытые пробелы (журнал 10.66/10.72/10.78). Большая часть — **чтение**, два блока требуют **записи** и **обязательного отката** (см. предупреждения).

> [!WARNING]
> Блоки **B2 (ремап)** и **B3 (2.4G запись)** пишут в память клавиатуры. Это ваша клавиатура — допустимо. Но: используйте **свежий бинарник** `target/release/kbc` (системный из PATH может быть старым), всегда делайте **readback** после записи и **в конце откатывайте** изменения (урок 10.81).

### 0. Сборка свежего `kbc`

```bash
cd keyboard-control
nix develop . --command cargo build --release
# бинарники: target/release/kbc, target/release/keyboard-center
# дальше в примерах: KBC="target/release/kbc" (или /home/darkside/keyboard-control/target/release/kbc)
```

Если с правами на hidraw проблемы — оборачивать команды: `sg plugdev -c "target/release/kbc …"`.

### B1. Индикаторы Caps/Num/Scroll (read-only, скриптом)

> **ВАЖНО:** у AULA F99 ролика громкости/энкодера **НЕТ** (живая диагностика: повтор поворота ролика не дал никаких изменений) — в сборе осталось только переключение индикаторов Caps/Num/Scroll и набор букв.

> **ВАЖНО (обновление 2026-09-20):** индикаторы Caps/Num/Scroll **НЕ находятся в конфиг-регионе 0x84** (дифф 11-config-diff.txt пустой). Это стандартный HID LED report — **Output report 0x02 на boot-интерфейсе (hidraw0)**. Для управления индикаторами нужно писать на hidraw0 (Usage Page 0x01, Usage 0x02 — Keyboard LEDs), а не через feature 0x06. Скрипт `collect-data.sh` обновлён, но дифф конфига для индикаторов **всегда пустой** — это ожидаемо.

Уже встроено в `scripts/collect-data.sh` (шаги 9–11): два read-only снимка конфига **до/после** переключения индикаторов и набора букв — результат в `11-config-diff.txt` (ожидаемо пустой).

```bash
./scripts/collect-data.sh --device f99 --sg
# 1) нажать Caps/Num/Scroll по одному разу,
# 2) набрать пару букв,
# 3) скрипт сам снимет снимок ПОСЛЕ и даст дифф.
# Результат: ~/kbc-diag-* / 11-config-diff.txt
```

Что искать в диффе: появившиеся байты за пределами эффект-таблицы `[58..125]` (например, рядом со служебными `[98..125]` или в `[0..57]`) — это и есть слот индикаторов. Пришлите этот дифф — код записи будет легко добавить.

> **Примечание:** для реального управления индикаторами нужно использовать `kbc raw 258A:010C output-send "02 00 <bitmap>"` на hidraw0 (bitmap: bit0=NumLock, bit1=CapsLock, bit2=ScrollLock). Это НЕ в конфиг-регионе 0x84.

### B2. Проверка W-канала ремапа (запись + ОТКАТ!) — **РЕЗУЛЬТАТ ПОДТВЕРЖДЁН НА ЖЕЛЕЗЕ**

На F75 запись работает через `06 03 <layer> …` + 512 байт слотов (10.62). На F99 **этот канал НЕ РАБОТАЕТ** — живая диагностика (журнал 10.82) показала:

```bash
$ KBC remap 258A:010C --key 73 --to 04
ошибка: устройство не поддерживает эту функцию
$ KBC remap 258A:010C --list | grep "слот  73"
слот  73 (0x49) → клавиша 0x2E (=)
```

- Команда `remap_key` (write 0x03) → `Unsupported` («устройство не поддерживает эту функцию»).
- Readback после попытки записи показывает **исходное значение** (0x2E) — слот не изменился.
- Откат `--key 73 --to 2E` тоже даёт `Unsupported`.

**Вывод:** канал записи ремапа F99 **не равен 0x03** (как у F75). Прошивка F99 блокирует/игнорирует запись через этот путь. Чтение keymap (0x83) работает нормально. Запись через `06 03` — закрыта.

> **Важно:** драйвер `aula_f99.rs` (строки 199, 205, 211, 217, 245, 251) уже честно возвращает `Err(Error::Unsupported(...))` для `remap_key`/`set_fn_layer` — код поведёт себя правильно (отказывает в записи, не ломает прошивку). Не нужно ничего менять в коде.

**Важно (2026-09-20):** запись ремапа через 2.4G-ресивер (`kbc remap 3554:FA09 ...`) **тоже не работает** — возвращает `Unsupported`. Канал записи ремапа на F99 **полностью отсутствует** (ни USB, ни 2.4G). Только чтение (0x83) работает.

Если владелец F99 найдёт другой канал записи (например, через другой CMD или 2.4G-ресивер) — обновим. Пока что: ремап на F99 = **read-only**.

### B2.5. Поиск канала записи ремапа (read-only дифф конфига в Windows-софте) — **КЛЮЧЕВОЕ**

**Цель:** найти, какой байт/канал меняется при записи ремапа через официальный Windows-софт AULA (или Fn-комбо, если есть). Это откроет запись ремапа в нашем драйвере.

**Что нужно:**
1. Запустить официальный Windows-софт AULA F99 (под Wine или на Windows).
2. Сделать снимок конфига **ДО** изменения раскладки:
   ```bash
   kbc raw 258A:010C feature-send "$(printf '06 84 00 00 01 00 80 00'; yes '00' | head -512 | tr '\n' ' ')"
   kbc raw 258A:010C feature-get 06 520 > config_remap_before.txt
   ```
3. В софте: переназначить одну клавишу (например, слот 73 «=» → «A»), **нажать «Применить/Сохранить в память»**.
4. Сделать снимок **ПОСЛЕ**:
   ```bash
   kbc raw 258A:010C feature-get 06 520 > config_remap_after.txt
   ```
5. Сравнить: `diff -u config_remap_before.txt config_remap_after.txt`

**Что ищем в диффе:**
- Изменения в конфиг-регионе (128 байт после хедера `84 00 00 01 00 80 00`).
- Конкретно: изменился ли `data[10]` (селектор эффекта) или байты слотов `data[8..519]` (512 байт keymap-таблицы).
- Если keymap-таблица меняется — запись ремапа идёт через **те же 0x03**, но, возможно, с другим флагом/подготовкой. Если меняется что-то другое — это новый канал.
- Пришлите оба файла + diff.

> **Важно:** снимок должен быть полным 520-байтовым пакетом (короткий SET не даёт ответа, журнал 10.3/10.20).

### B2.6. Поиск байтов индикаторов Caps/Num/Scroll (read-only дифф)

**Цель:** найти, где в конфиге живут биты состояния индикаторов (LED Caps/Num/Scroll).

**Что нужно:**
1. Снимок конфига **ДО** нажатий (как выше, `config_ind_before.txt`).
2. Физически на клавиатуре: по одному разу нажать-отпустить **Caps Lock, Num Lock, Scroll Lock**.
3. Снимок **ПОСЛЕ** (`config_ind_after.txt`).
4. `diff -u config_ind_before.txt config_ind_after.txt`

**Что ищем:** появившиеся/изменённые байты в `[0..57]` (до эффект-таблицы) или в служебной зоне `[98..125]`. Это даст адрес для `set_indicator`.

### B2.7. Debounce / sleep timer (read-only дифф, если есть Fn-комбо или софт)

**Цель:** найти байты debounce и sleep timer в конфиге.

**Что нужно:**
1. Снимок конфига **ДО** (`config_db_before.txt`).
2. В Windows-софте (или Fn-комбо, если работает): сменить debounce и/или sleep timer.
3. Снимок **ПОСЛЕ** (`config_db_after.txt`).
4. `diff -u config_db_before.txt config_db_after.txt`

**Что ищем:** изменённые байты в конфиг-регионе. По cloudglides (F75) debounce = frame0 byte8, sleep = frame1 byte15 (минуты×2) на 2.4G; на USB — ищем аналоги.

### B2.8. Per-key RGB на 2.4G (опционально, read-only дифф ресивера)

**Цель:** понять формат записи per-key цвета через ресивер (канал `0x02/0x1C` по dnviti).

**Что нужно:**
1. Подключить ресивер `3554:FA09`, клавиатура в 2.4G, **не спать** (нажать клавишу).
2. Снимок LED-config ресивера **ДО** (`kbc raw 3554:FA09 feature-get 06 520 > led_before.txt` или через 0x44).
3. В Windows-софте: задать per-key цвета (разные клавиши — разные цвета), «Применить».
4. Снимок **ПОСЛЕ** (`led_after.txt`).
5. `diff -u led_before.txt led_after.txt`

**Что ищем:** какие байты в payload меняются (палитра, слоты, флаги).

### B2.9. Интерактивные 2.4G-тесты через collect-data.sh (ресивер 3554:FA09)

**Цель:** проверить работоспособность 2.4G-функционала (батарея, RGB-эффекты, яркость, скорость, выбор эффекта, гашение света) на живой клавиатуре в режиме 2.4G.

Скрипт `collect-data.sh` имеет встроенную секцию 2.4G-тестов, которая запускается автоматически при `--device f99 --sg`, если ресивер `3554:FA09` обнаружен в `kbc list`.

**ПОДГОТОВКА (ОБЯЗАТЕЛЬНО перед запуском):**
1. Переключите клавиатуру в режим **2.4G** (на F99: `Fn+1` / `Fn+2` / `Fn+3` / `Fn+4` — выбор канала; по умолчанию канал 1 = `Fn+1`).
2. Убедитесь, что ресивер `3554:FA09` подключен к ПК.
3. Клавиатура должна быть **спейрена** с ресивером (из коробки они уже спейрены; если нет — см. мануал).
4. Клавиатура должна быть **НЕ спать** — перед запуском нажмите **ЛЮБУЮ клавишу** (пробуждение линка).

**Что тестируется (пошагово, с подтверждением владельца):**

| Шаг | Команда | Что проверяет |
|---|---|---|
| **2.4G-0** | `kbc battery 3554:FA09` (пробуждение) | Проверка готовности линка: разбудить клавиатуру, получить процент батареи. Если «спит на линке» — клавиатура не в 2.4G или спит. |
| **2.4G-1** | `kbc battery 3554:FA09` | Батарея ресивера (протокол 0x13, cmd 0x05→0x0A). Ожидается процент (100% и т.д.). |
| **2.4G-2** | `kbc rgb 3554:FA09 --mode breathing --brightness 200 --speed 60` | Запись эффекта **Breathing** в память ресивера (протокол 0x13, `apply_rgb_persistent`). Эффект должен быть виден визуально (плавное дыхание) и держаться без приложения. |
| **2.4G-3** | `kbc rgb 3554:FA09 --light-off` / `--light-on` | Гашение и включение света с сохранением в память (протокол 0x13, `apply_light_persistent`). Проверка: свет погасает/загорается, сохраняется после переподключения. |
| **2.4G-4** | (read-only заметка) | Чтение LED-config (0x44) и RGB-table (0x49) ресивера требует **output report 0x13** (многостраничный протокол), который `kbc raw feature-get` **не поддерживает** (feature 0x06 возвращает константный блок). См. `aula_f75.rs::wl_read_pages`. |
| **2.4G-5** | Справочник | Файл `35-wl-effects-list.txt` — коды `led[10]` (WL_EFFECTS) для 20 эффектов 2.4G (0x01–0x1E). |

**Запуск:**
```bash
# 1. Переключите клавиатуру в 2.4G (Fn+1), нажмите клавишу
# 2. Ресивер подключен
# 3. Запуск:
./scripts/collect-data.sh --device f99 --sg
# Секция 2.4G запустится автоматически после B2.8
```

**Ожидаемые файлы в архиве:**
- `30-battery-2g4.txt` — батарея 2.4G (после пробуждения)
- `31-rgb-breathing.txt` — тест Breathing (запись в память)
- `32-light-off.txt` / `33-light-on.txt` — гашение/включение света
- `34-led-config-2g4.txt` — заметка про 0x13 protocol
- `35-wl-effects-list.txt` — справочник WL_EFFECTS (коды led[10])

> **ВАЖНО:** если `kbc list` показывает только ресивер `3554:FA09` без клавиатуры `258A:010C` — клавиатура **не в режиме 2.4G** или не спейрена. Переключите `Fn+1` и нажмите клавишу.

### B2.10. Реверс-диагностика USB-канала скриптом `f99-usb-rev.sh` (по желанию, с write-тестами)

**Цель:** закрыть открытые вопросы USB-канала F99 — (1) аппаратная запись конфига `06 04` и наличие latch, (2) управление индикаторами Caps/Num/Scroll через boot output-report, (3) нахождение селектора `data[10]` для per-key self-define цветов (color table `06 8A/0A`).

Скрипт `scripts/f99-usb-rev.sh` собирает тот же read-only набор (дампы конфига/цветов/keymap, probe, lsusb), что и `collect-data.sh`, но дополнительно умеет **write-тесты T1–T3** (только с флагом `--write-tests`). Каждый тест после себя **восстанавливает исходные данные**, маркер `5A A5` (data[126..127]) не трогается.

> Те же write-тесты можно запустить прямо из основного скрипта: `./scripts/collect-data.sh --device f99 --sg --write-tests` — `collect-data.sh` сам делегирует их в `f99-usb-rev.sh` (см. `docs/collect-data.md`, раздел 0).

```bash
# read-only (безопасно, ничего не пишет):
./scripts/f99-usb-rev.sh --device f99 --sg

# с write-тестами (перед каждым задаёт вопросы y/N, требуем подтверждения):
./scripts/f99-usb-rev.sh --device f99 --sg --write-tests
```

| Тест | Что делает | Что ищем |
|---|---|---|
| **T1** | Запись конфига `06 04`: выставляет селектор `data[10]=0x03`, readback, визуальная проверка, ВОССТАНОВЛЕНИЕ | Работает ли аппаратная запись конфига у F99 и есть ли latch (кик клавиатуры = commit) |
| **T2** | Индикаторы через boot output-report: `02 02 00 00 00 00 00 00` (bit1=CapsLock зажжён) → визуальный вопрос → гашение | Переносятся ли индикаторы на boot-канал (в конфиге их нет) |
| **T3** | Запись красного `FF 00 00 00` ×3 в начало color table (`06 0A`), readback, затем Fn+`\` до однотонного эффекта → снимок конфига | **Реальный селектор `data[10]` для static/self-define** — чтобы оживить `set_rgb_color` в `aula_f99.rs` |

**Write-форматы (критично при ручном повторении):**
- конфиг: `06 04 00 00 01 00 80 00` + **128 байт data** (только поля 9..NF строки ответа, без report id/header) + 384 нуля = ровно **520**;
- color table: `06 0A 00 00 01 00 00 02` + **512 байт** = ровно **520** (пад НЕ нужен);
- `data[i]` ответа = поле **i+8** строки (data[10] = поле 19).

**Что прислать после прогона:** свежий архив `~/kbc-diag-<дата>-<время>.tar.gz` + итоговое сообщение скрипта о результатах T1–T3 (что показала визуальная проверка, какой `data[10]` дал T3).

### B3. Debounce / sleep timer (read-only look + аккуратная проба)

- **USB-канал** для debounce/sleep у F75/F99 не найден ни в одном источнике — оставлен честным `Unsupported` (10.67). Если Fn-комбинации на F99 меняют debounce/sleep — снять конфиг до/после тем же дифф-приёмом (B1), ищем новый меняющийся байт рядом с эффект-таблицей.
- **2.4G-ресивер**: по cloudglides debounce = frame0 byte8, sleep = frame1 byte15 (минуты×2) — **не подтверждено**. Read-only дифф: снять LED-config ресивера (readback через `kbc raw` на `3554:FA09`) до/после смены значения в Windows-софте — если есть такая возможность.

## C. Формат передачи цветов (полная инфа для интерпретатора)

Это ядро host-подсветки — то, что нужно знать, чтобы написать свой генератор кадров (GIF и т.п.).

### C1. Тип данных в коде

```rust
pub struct Color { pub r: u8, pub g: u8, pub b: u8 }   // RGB888, макс 255
```

- Один кадр — `Vec<Color>` из **ровно 113 элементов** (F99, `RGB_LED_COUNT = 113`).
- Индекс — номер светодиода в матрице **96% с NumPad** (порядок по OpenRGB `aula_f99_layout`). Это НЕ порядок строк/сетки — линейный список LED.
- Координат нет — только список 113 цветов.
- Точка входа: `fn render_frame(&self, colors: &[Color]) -> Result<()>` — `src/devices/aula_f99.rs:184`.

### C2. Физический HID-пакет

```
Feature report, id 0x06, РОВНО 520 байт.
[0] = 0x06              (report id)
[1] = 0x08              (команда «прорисовка кадра» / direct)
[2] = 0x00  [3] = 0x00  [4] = 0x01  [5] = 0x00  [6] = 0x7A  [7] = 0x01
[8..] = тройки RGB: r g b r g b … (3 байта на LED)
        113 × 3 = 339 байт
далее — пад нулями до 520 байт
```

- Отправка — `hid_send_feature_report` (send_feature), НЕ output.
- Значение `0x7A` = «122» (число зон прямой прорисовки), `0x01` — zone. Для F75 буфер 90 LED, у F99 — 113.

### C3. Скорость и keepalive (критично!)

- Кадры идут потоком **~20–25 FPS** (таймер 40 мс; CLI hold 40 мс — журнал 10.71).
- **Если поток остановить (~1 с)** — клавиатура уходит из direct-режима и возвращается к аппаратному эффекту (10.7). То есть интерпретатор GIF должен **непрерывно слать кадры**, пока подсветка должна жить.
- GIF: ресайз кадра на карту из 113 точек (по макету 96%, не по сетке), децимировать целевую скорость с учётом задержек кадров GIF (единицы мс из блока Graphic Control Extension), затем в цикле `render_frame(&frame)` каждые 40 мс.

### C4. Пример (псевдо-вызов из драйвера)

```rust
// ваш GIF-парсер даёт кадр 113 цветов (порядок LED по OpenRGB aula_f99_layout)
let frame: Vec<Color> = gif_frame_to_113_leds();   // 113 × Color
kbd.render_frame(&frame);                           // сам делает пакет + пад + send
```

Парсер GIF уже есть в проекте: `src/screen/converter.rs` (для экрана Ajazz). Оттуда можно взять декодер GIF/преобразование RGB→RGB565 и переиспользовать — не изобретайте заново.

### C5. Почему «в память не пишется»

Это **host-рендеринг**: кадры живут, пока процесс шлёт поток. В EEPROM клавиатуры сохраняются только аппаратные радужные эффекты прошивки (селектор `data[10]`, слоты `[58..125]`). Статика/свой GIF в память не пишутся — это физика прошивки, а не ограничение софта (10.24/10.36).

## D. Участие в проекте (ответ на «могу ли я оформить md / принять PR»)

**Да, конечно.** Проект MIT, вклад от владельцев железа приветствуется. Как лучше:

1. **Оформить md** — можно, стиль такой: заголовок `#`, блоки > [!WARNING]/[!IMPORTANT] `/ [!NOTE]`, русский язык, минимум лишнего. Идеально — новый файл в `docs/` или дополнение `docs/collect-data.md` (если это про сбор данных).

4. Присылайте снимки/диффы из разделов B — они важнее текста: по ним дорабатываются драйверы.
